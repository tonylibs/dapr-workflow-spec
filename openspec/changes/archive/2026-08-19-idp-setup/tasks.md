## 3. Dex config and bootstrap-admin Secrets

- [x] 3.1 Add `charts/dws/templates/dex/secrets.yaml` (combining what were planned as two separate files — see 3.3), gated on `.Values.dex.enabled`, rendering the config Secret named `.Values.dex.configSecret.name` with `data: {config.yaml: <base64 of dws.dex.config output>}`, matching the upstream `dex` chart's own `secret.yaml` shape exactly (`data`, not `stringData`) so `configSecret.create: false` + this Secret name is a drop-in replacement.
- [x] 3.2 In the same file, gated additionally on `(not .Values.dex.adminUser.existingSecret)`, render `<dws.dex.adminCredentials.fullname>` with `stringData: {email, password}` sourced from `dex.adminUser.email` and the resolved password.
- [x] 3.3 Confirmed against the real `charts/dws` chart (`helm template dws charts/dws --set dex.enabled=true`) that the admin-credentials Secret's plaintext password and the config Secret's decoded `staticPasswords[].hash` are derived from the same generated value in a single render pass — `bcrypt.checkpw(password, hash)` on the actual rendered output returns `True`. Also confirmed the `dex` subchart's Deployment mounts `volumes[].secret.secretName: dex-config`, matching the Secret this change renders. **Design correction made during implementation**: `include` is not memoized in Helm — the originally planned "call the same named template from both files" would silently call `randAlphaNum` twice per render, producing two *different* passwords whenever `lookup` finds nothing (i.e. every `helm template`, and every real first `helm install`) — caught first via a standalone smoke-test chart before real subchart access was available. Fixed by computing the password once as a `$password` variable in a single template file and passing it explicitly into both renders. design.md's D2/D3 and this file's task 2.2/3.1 text were updated to match.
